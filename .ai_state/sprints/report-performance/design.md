# 日报剩余性能优化（2026-10-17）

## Scope

- 用户要求继续已确认性能清单剩余项：Git 先筛选/批量详情、日报流式正文、数据库按需与合并持久化。
- 基线 `902e1c4`，第一轮已由用户提交，当前工作区干净。隔离实施目录 `.cache/worktrees/report-performance`，完成后同步 dev，不提交或推送。
- 不新增依赖、不更换数据库或 AI 协议、不扩大到周总结/反思/素材日报链路重构；沿用 Chat Completions、作者日期、保存/取消/发布语义与第一轮启动优化。

## Design

1. Git 日志读取保留现有 committer 粗筛与 author 精筛、非 merge 提交规则。按名称或邮箱先筛选，所需详情以有界批次读取，保留每条 4000 字符与汇总 12000 字符上限。无匹配时不调用详情命令，保留时间窗内总数用于原提示。不要建立第二条采集路径。
2. AI 使用现有 HTTP transport 与超时机制，超时持续覆盖响应体消费。日报发送 stream=true，解析 SSE 的分片 UTF-8、data 行、结束标记与错误；同一次响应如果服务端返回既有 JSON 可正常读取，不为失败流自动发第二个生成请求。
3. 生成生命周期保持一个 Promise：先通知采集阶段，再流式显示正文；正文完成后显示整理/保存状态，元数据提取不阻塞正文展示。最终生成结果、historyId 和保存状态仍在持久化成功后返回，避免后台任务晚到覆盖手工编辑。元数据失败维持当前可降级行为。
4. IPC 进度仅发给原请求窗口，按 requestId 匹配；订阅先于调用并在成功/失败/取消时清理。日报与批量日报共用 projectReportActions，生成期间只读预览流文本，保存前保留原草稿，失败/取消不把半篇正文标记为已保存。不能跨项目串流或泄漏监听器。
5. 数据库初始化比较实际 schema/数据变化，仅有变化时原子持久化。持久化队列将同批待保存请求共享一次快照；写入过程中产生的后续变更必须在下一次快照完成后才确认成功。失败对相关调用方可见，队列仍能恢复。保持原子文件写入和重启恢复数据安全。

## Acceptance Criteria

- AC1: 真 Git 仓库验证姓名/邮箱 OR 匹配、作者日期边界/rebase 日期、无匹配、多个提交详情不串；详情进程数按批次而不是提交数增长。
- AC2: 分片到达时前端可看到正文，元数据 Promise 未完成时正文仍可见且显示未完成状态；不标记保存/发布成功，最终成功才携带 historyId。
- AC3: 并发项目/日期按 requestId 隔离；失败、超时、取消、页面离开、晚到事件不会覆盖原草稿或串入新任务；不会重复生成 AI 请求，监听器能清理。
- AC4: SSE 流消费在真实本地 HTTP 分片服务或可控 ReadableStream 上验证，包括断流、取消、UTF-8 分割、HTTP 错误；既有非流式请求与错误提示不回归。
- AC5: 已迁移且无变化数据库重启不导出/写库；新库/迁移/缺失快照仍保存；并发批次减少导出次数、最终数据重开一致，写中变更/失败恢复覆盖。
- AC6: 相关单测、完整可靠性测试、类型/构建、日报和批量日报浏览器回归、真实隔离 Electron/持久化验证通过；记录过程/数量证据，不把机器时间外推为安装包或远程 AI 时延承诺。
