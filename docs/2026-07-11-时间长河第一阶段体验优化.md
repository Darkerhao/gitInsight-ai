# 时间长河第一阶段体验优化方案

更新日期：2026-07-11  
适用页面：成长中心 / 时间长河  
阶段目标：优先解决信息难读、详情难扫、节点重复、指标不明和空间利用率低的问题。

## 1. 背景

时间长河页面以年度开发轨迹为核心，通过纵向时间轴呈现 Git 提交和 AI 归纳后的工作事项，并在右侧展示选中事项详情。当前版本已经建立了较强的沉浸式视觉风格，但信息表达仍偏向展示大屏，业务页面所需的可读性、浏览效率和信息结构不足。

第一阶段不调整页面核心概念，不引入新的复杂分析能力，也不重构整体导航。优化重点是让用户能够更快完成以下任务：

1. 看清时间轴中的日期、类型、项目和工作内容。
2. 快速理解选中事项的主要成果和影响范围。
3. 区分同一天、同一模块下的多项工作。
4. 理解节点数值和底部统计指标的业务含义。
5. 在不同分辨率下合理利用页面空间。

## 2. 第一阶段范围

### 2.1 本阶段包含

- 提升时间轴文字的字号、对比度和信息层级。
- 将右侧详情由连续长文本改为结构化内容。
- 对同日、同项目或同模块事项进行聚合展示。
- 明确节点数字、标签及统计数据的含义。
- 优化时间轴、详情面板和空白区域的空间分配。
- 强化当前选中节点及其详情之间的视觉关联。
- 补充基础响应式和内容溢出规则。

### 2.2 本阶段不包含

- 月份快速导航和时间轴缩略图。
- 年度、月度、单日视图逻辑重构。
- 成长能力趋势、同比或环比分析。
- 轨迹回放控制体系升级。
- 数据来源追踪、关联 Commit 查看和 AI 重新生成。
- 星空背景及 WebGL 动效的整体重构。

以上内容可在后续阶段单独规划。

## 3. 现状问题

### 3.1 时间轴信息可读性不足

- 非选中节点的文字透明度过低，在深色背景下难以辨认。
- 项目名、事项类型、标题、摘要和日期之间缺少稳定层级。
- 节点两侧文本宽度不足，标题和摘要过早截断。
- 发光主轴的视觉强度高于实际内容，用户注意力容易停留在装饰效果上。

### 3.2 详情内容缺少结构

- “今日工作内容”以连续长段落展示，扫描成本高。
- 功能开发、Bug 修复、优化内容和明日计划混合在同一区域。
- 事项成果、技术动作和业务影响没有明确区分。
- 卡片上半部分文字密集，下半部分大面积空置。

### 3.3 重复节点缺乏聚合

- 同一天可能出现多个日期相同、类型相近的节点。
- 用户无法快速判断节点代表一次 Commit、一项工作还是一份日报。
- 大量零散节点会拉长时间轴，降低年度轨迹的浏览效率。

### 3.4 指标语义不明确

- 节点中的 `78`、`88`、`94`、`100` 等数字没有名称和单位。
- 底部 `COMMITS`、`ACTIVE DAYS` 等指标字号过小，且与时间轴缺少关联。
- 数字接近满值时难以体现差异，也无法帮助用户作出判断。

### 3.5 空间分配不合理

- 时间轴内容集中在中部窄区域，超宽屏两侧存在大量无效空白。
- 右侧详情卡固定占用较大面积，但内容未充分利用垂直空间。
- 左右交替节点与详情卡之间距离过大，页面信息关系松散。

## 4. 优化目标

| 目标 | 期望结果 |
| --- | --- |
| 信息可读 | 默认状态下无需悬停即可识别日期、类型、项目和标题 |
| 内容易扫 | 用户可在 5 秒内判断选中事项的工作成果、分类和影响范围 |
| 结构清晰 | 同日同模块事项聚合，主时间轴优先表达工作主题而非零散记录 |
| 指标明确 | 所有节点数字均有名称、单位和解释，装饰性数字不进入正式界面 |
| 空间高效 | 时间轴与详情区域形成稳定双栏布局，减少无意义空白 |
| 状态明确 | 当前选中节点、对应详情和类型颜色保持一致 |

## 5. 详细优化方案

### 5.1 时间轴信息层级

单个时间轴事项统一使用以下层级：

```text
事项类型 · 项目名称
事项标题
事项摘要（最多两行）
日期 / 事项数量
```

建议视觉规格：

| 元素 | 建议规格 | 说明 |
| --- | --- | --- |
| 类型与项目 | 12–13px / 600 | 使用类型语义色，不使用过低透明度 |
| 事项标题 | 16–18px / 600 | 节点主要识别信息，最多两行 |
| 事项摘要 | 13–14px / 400 | 最多两行，超出显示省略号 |
| 日期 | 12–13px / 500 | 与节点保持固定距离，格式统一为 `07.01` |
| 辅助信息 | 12px / 400 | 默认对比度仍需满足正常阅读 |

基础规则：

- 主要文字与背景的对比度建议不低于 WCAG AA 普通文本要求。
- 非选中节点正文不应通过降至极低透明度来弱化，建议不低于 `60%` 的视觉不透明度。
- 单侧文本区域建议宽度为 `320–420px`，根据窗口宽度动态变化。
- 摘要最多展示两行；悬停、聚焦或点击后可查看完整内容。
- 对于没有摘要的事项，不保留空白占位。
- 节点之间的最小垂直间距应根据文本实际高度计算，避免固定位置造成重叠。

### 5.2 当前选中状态

选中节点需要同时改变节点、文字和详情面板状态：

- 节点相对默认状态放大约 `1.1–1.15` 倍。
- 节点描边、事项类型文字和详情卡强调线使用同一语义色。
- 选中事项标题使用高亮文字色，摘要保持正常可读。
- 非选中节点只降低强调程度，不应变成不可读背景。
- 鼠标悬停与正式选中需区分：悬停仅预览强调，点击后才更新右侧详情。
- 键盘聚焦状态必须有独立描边，不完全依赖颜色表达。

### 5.3 同日事项聚合

时间轴的一级节点建议表示“日期”，二级内容表示该日的模块或工作事项。

默认聚合规则：

1. 先按日期聚合。
2. 同一日期内按项目或业务模块聚合。
3. 同一模块内按工作类型归类，例如功能开发、Bug 修复、重构优化。
4. 一级节点显示当天综合摘要和事项总数。
5. 点击一级节点后，在节点附近或详情面板中展开具体事项。

示例：

```text
2026-07-01 · 5 项工作
资产看板 API 与列表能力建设

- 功能开发 3 项
- Bug 修复 1 项
- 重构优化 1 项
```

聚合后的标题应由 AI 摘要或已有日报标题生成，但必须满足：

- 表达工作主题，避免使用“今日工作内容”等无区分度标题。
- 优先包含业务模块和成果，例如“资产看板 API 与列表能力建设”。
- 最多两行，不直接拼接所有 Commit message。
- 当天只有一项工作时可直接展示事项，无需额外增加聚合层级。

### 5.4 右侧详情结构化

详情面板建议拆分为固定信息区和可滚动内容区。

#### 顶部固定信息

- 日期。
- 工作类型。
- 项目或仓库名称。
- 事项标题。
- 可选状态或评分说明。

#### 中部可滚动内容

按照实际存在的数据展示以下区块，不存在的区块不渲染：

1. 工作成果。
2. 功能开发。
3. Bug 修复。
4. 重构与性能优化。
5. 影响范围。
6. 风险与待确认项。
7. 明日计划。

内容规范：

- 每个区块使用短列表，不使用一整段连续文本。
- 单条内容优先使用“动作 + 对象 + 结果”的表达方式。
- 技术实现细节和业务成果分开描述。
- 项目名、接口名、组件名、类型名等技术标识符保持原始格式。
- 单条建议控制在 1–3 行，超过时允许展开查看。
- 内容区独立滚动，底部统计和操作按钮保持可见。

示例：

```text
工作成果
- 完成资产看板 6 个 API 接口开发，支持执行列表及多条件筛选。
- 补齐列表字段和状态展示，提升数据识别效率。

Bug 修复
- 修复无效接口描述被纳入统计的问题，降低日报噪声。

影响范围
- 资产看板
- 列表查询
- 日报生成
```

### 5.5 节点数字和统计指标

节点中的数字必须对应明确业务指标，可选择以下一种语义：

- 工作完成度，例如“完成度 94%”。
- AI 内容质量评分，例如“质量分 94”。
- 当日贡献指数，例如“贡献指数 94”。
- 当日 Commit 数量，例如“8 次提交”。

不得仅显示裸数字。若当前数字没有可信、稳定、可解释的计算方式，第一阶段建议直接移除，改为显示“事项数量”或“提交数量”。

若保留评分，需要提供：

- 指标名称和单位。
- 悬停说明或帮助入口。
- 评分计算维度。
- 数据缺失状态，禁止用 `0` 冒充暂无数据。

底部统计建议移至标题区域下方，形成页面概览：

```text
84 次提交 · 9 个活跃日 · 18 项工作 · 3 个活跃项目
```

第一阶段可以仅调整位置、中文文案和可读性，不要求增加新的统计维度。

### 5.6 页面空间布局

桌面端建议采用“时间轴主区域 + 详情侧栏”的双栏结构：

```text
┌──────────────────────────────────────────────┐
│ 页面标题、筛选器、视图控制                   │
├───────────────────────────────┬──────────────┤
│                               │              │
│       时间轴主区域             │  详情面板    │
│                               │              │
│                               │              │
└───────────────────────────────┴──────────────┘
```

建议参数：

- 详情面板宽度使用 `clamp(360px, 24vw, 440px)`。
- 时间轴主区域占据剩余空间，内部内容设置合理最大宽度。
- 时间轴中心线可相对主区域居中，不应相对整个页面居中。
- 详情面板与页面右侧保留 `24–32px` 间距。
- 主区域与详情面板间距建议为 `24–40px`。
- 超宽屏下限制主内容最大宽度，避免节点文字与中心线距离无限扩大。
- 详情面板支持收起；收起后时间轴主区域自动扩展。

响应式规则：

- 当内容区宽度低于约 `1280px` 时，缩小节点文本宽度并减少左右间距。
- 当内容区宽度低于约 `1024px` 时，详情面板改为覆盖式抽屉。
- 窄屏状态下时间轴改为单侧排列，避免左右交替导致内容过窄。

### 5.7 背景与发光效果约束

第一阶段保留现有星空视觉，但对影响阅读的效果进行收敛：

- 降低非选中节点和主轴持续发光强度。
- 最强发光效果只用于当前选中节点。
- 文本背后避免出现高亮星点或明显光斑。
- 星点动画不得造成文字明暗持续变化。
- 用户开启系统“减少动态效果”时，关闭闪烁、漂移和持续脉冲动画。

## 6. 状态与边界处理

### 6.1 加载状态

- 时间轴加载时使用与最终布局一致的骨架屏，避免页面明显跳动。
- 详情区域未选中节点时展示引导语，不显示空白大卡片。
- 聚合数据生成中应明确提示“正在整理当日工作事项”。

### 6.2 空状态

- 当前筛选无数据时，显示筛选条件说明和“清除筛选”入口。
- 当前年度无数据时，引导用户生成日报或检查 Git 仓库配置。
- 不使用只有星空背景而没有解释的空页面。

### 6.3 异常与缺失数据

- 缺少项目名时显示“未识别项目”，不能留空。
- 缺少工作类型时归入“其他工作”，并允许后续修正。
- 缺少摘要时只展示标题，不重复标题作为摘要。
- 评分或统计不可用时显示“暂无数据”，不显示误导性的 `0`。

## 7. 建议组件拆分

以下仅作为实现边界建议，不要求第一阶段立即大规模重构：

| 组件职责 | 建议组件 |
| --- | --- |
| 页面标题、概览指标和筛选 | `ChronicleHeader` |
| 时间轴容器及节点布局 | `ChronicleTimeline` |
| 日期聚合节点 | `ChronicleDayNode` |
| 单项工作摘要 | `ChronicleWorkItem` |
| 右侧结构化详情 | `ChronicleDetailPanel` |
| 类型标签及语义色 | `WorkTypeTag` |
| 指标名称与解释 | `MetricValue` |

重点是将数据聚合、节点布局和详情展示分离，避免单个页面组件同时承担数据处理、动画和长文本渲染。

## 8. 数据结构建议

页面展示层建议消费已经聚合的日期模型：

```ts
interface ChronicleDay {
  date: string
  title: string
  summary?: string
  projectNames: string[]
  workItems: ChronicleWorkItem[]
  commitCount?: number
  metric?: {
    label: string
    value: number
    unit?: string
    description?: string
  }
}

interface ChronicleWorkItem {
  id: string
  type: 'feature' | 'bugfix' | 'refactor' | 'performance' | 'engineering' | 'other'
  projectName?: string
  title: string
  summary?: string
  achievements?: string[]
  impacts?: string[]
  risks?: string[]
  nextPlans?: string[]
}
```

如果当前后端只能返回连续文本，可先在前端兼容旧数据，但不建议长期通过正则解析自然语言段落。结构化内容应逐步由日报生成结果或持久化数据直接提供。

## 9. 验收标准

### 9.1 可读性

- 在 `1920×1080` 分辨率和 100% 系统缩放下，非选中节点的日期、类型、项目名和标题均可直接辨认。
- 时间轴标题不小于 `16px`，摘要不小于 `13px`。
- 文本不会与节点、日期、星点或相邻事项发生视觉重叠。
- 长标题和长摘要具有一致的截断与完整内容查看方式。

### 9.2 信息结构

- 同一天存在多项工作时，主时间轴只出现一个日期级入口。
- 当天事项可按项目或模块查看，不直接堆叠全部 Commit。
- 详情内容按工作成果、工作类型、影响范围和计划等区块展示。
- 不存在数据的详情区块不会显示空标题或空占位。

### 9.3 指标语义

- 页面不存在没有名称和单位的裸数字指标。
- 每个评分型指标均可查看含义和计算说明。
- 数据缺失与真实数值 `0` 有明确区别。
- 底部或顶部汇总指标使用中文业务文案。

### 9.4 布局与响应式

- `1366×768`、`1440×900`、`1920×1080` 和超宽屏下无横向滚动条。
- 详情面板内容过长时仅内部滚动，关键操作保持可见。
- 详情面板收起后，时间轴区域能够自动扩展。
- 内容区宽度不足时，详情切换为抽屉且时间轴可正常浏览。

### 9.5 交互状态

- 点击节点后，节点、标题和详情强调色一致。
- 悬停状态与选中状态可以明确区分。
- 键盘聚焦状态清晰可见。
- 未选中事项、加载、空数据和异常状态均有明确反馈。

## 10. 实施顺序

### P0：立即改善核心可用性

1. 提升时间轴文字字号、颜色和对比度。
2. 调整节点文本宽度、截断规则和垂直间距。
3. 将详情长段落拆分为结构化区块。
4. 为节点数字增加明确名称和单位；无法解释时移除。
5. 强化节点选中状态与详情面板关联。

### P1：整理信息结构

1. 按日期聚合时间轴数据。
2. 同日内容按项目、模块和工作类型归类。
3. 增加聚合节点展开与单事项选择能力。
4. 统一空状态、缺失数据和异常展示。

### P2：优化空间和响应式

1. 将时间轴中心线改为相对主内容区定位。
2. 调整详情面板宽度和内部滚动区域。
3. 增加详情面板收起状态。
4. 完成 `1366×768` 至超宽屏的响应式适配。
5. 收敛影响阅读的背景和发光效果。

## 11. 风险与注意事项

- 日期聚合可能改变现有节点与日报记录的一一对应关系，需要保留稳定的事项 ID。
- 详情结构化依赖数据源质量，不能仅在视觉层把连续文本强行切段后视为完成。
- 如果节点数字来自 AI 评分，应先确认评分是否稳定、可解释，再决定是否保留。
- 时间轴使用绝对定位或 Canvas/WebGL 绘制时，动态内容高度可能导致节点重叠，需要提前验证布局方案。
- 动效调整应同时关注低性能设备和系统“减少动态效果”设置。
- 优化过程中应保留当前视觉主题的辨识度，避免将页面改造成普通列表页。

## 12. 完成定义

第一阶段完成应同时满足：

- 用户无需放大页面即可读懂时间轴主要内容。
- 用户可以快速扫描详情，而不是阅读连续长段落。
- 同日重复节点得到聚合，年度轨迹明显更简洁。
- 所有数字和指标具备清晰业务含义。
- 页面在常见桌面分辨率下空间分配合理。
- 加载、空数据、异常和选中状态均有明确反馈。
- 通过人工视觉检查和对应的前端自动化检查，不引入现有时间轴交互回归。
